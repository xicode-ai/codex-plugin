# 业务知识正文写作规范

目标读者是产品经理、运营人员和询问业务问题的用户。知识库只按段落或整句切分 Markdown，因此文档既要有阅读层次，业务规则片段也要保留必要上下文。源代码只用于反推和核对，不能出现在导入正文中。

## 目录与资料边界

```text
output/
  README.md                         阅读导航、实际分析范围、导入说明
  knowledge/
    system-overview.md              系统定位、业务目标与范围
    glossary.md                     必要的业务术语
    modules/<模块>/overview.md      模块职责、能力及上下游
    modules/<模块>/<主题>.md        具体业务场景、流程和规则
    cross-system/<场景>.md          经核实的跨系统协作及边界
  analysis/
    analysis.json                   源码证据、结论、场景、覆盖与文档映射
    knowledge-manifest.json          稳定 ID、文件哈希、版本和维护清单
    questions-and-conflicts.md       假设、冲突和调查缺口
    diagrams/                       可选图源及渲染图片
```

knowledge/ 只放要入库的业务 Markdown；analysis/ 由分析者保留，不导入业务知识库。只生成适合实际系统的模块与主题，不按仓库数量推定模块数，也不逐个接口、类或数据表建页面。一个有独立业务意义的主题一份文档，细规则在主题内分节；避免总览、模块和主题整段复制同一答案。

## 必须能读懂的 Markdown 层次

每份文档用一个一级标题表明主题，再按业务问题组织二级小节。需要时用三级标题展开，不得只有一级标题加一串同构句子。小节下用空行分开的完整说明段落解释业务；编号列表表达流程，表格比较条件，二者不能替代所有解释。不要把大段文字装进代码块，也不要把整页写成条目、表格或字段清单。

| 文档 | 主要内容与可选小节 |
| --- | --- |
| 系统总览 | 系统定位、服务对象、业务范围、核心模块、系统协作、业务终点与边界 |
| 模块说明 | 模块职责、使用场景、主要能力、关联对象、上游输入与下游结果 |
| 业务主题 | 适用场景、参与角色、前置条件、业务流程、业务规则、异常处理、结果与后续 |
| 跨系统场景 | 业务目标、各方职责、协作步骤、交接确认、失败与边界 |
| 术语 | 按业务对象或状态含义分组，解释概念与区别，避免逐行枚举程序常量 |

这些是内容检查方向，不强迫所有文档出现同名标题。篇幅取决于已确认的业务复杂度，不能靠增加空标题、固定字数、无关背景或未经核实的 FAQ 凑完整。缺少核心证据就继续调查或标明范围，不把简短代码摘要包装成详细功能说明。

## 从实现行为综合成业务说明

写每个主题前先在 analysis/ 回答：谁在什么场景操作什么对象；满足哪些条件；流程如何推进；结果由谁确认；失败后谁处理。随后将分散在多个实现位置的事实综合为业务流程，按用户目标组织正文，而不是逐条翻译调用语句。

实现名词与业务表达的转换方向：

| 实现线索（只在分析资料中） | 知识正文应解释的业务意义 |
| --- | --- |
| 控制器、接口路径、方法调用 | 用户可发起什么业务操作，何时可发起 |
| 状态常量、比较条件、数据字段 | 单据的业务阶段、可操作范围、必填业务信息 |
| 锁、线程池、队列、数据库更新方式 | 重复申请如何处理、批量申请是否逐笔完成、用户何时得知结果 |
| 外部客户端调用 | 哪个业务系统承接下一步，接收申请与完成业务的区别 |
| 异常分支与补偿 | 申请为什么会被拒绝、失败后如何恢复或由谁介入 |

转换必须有相应实现证据，不能看到防并发设施就编出防资损动机，也不能看到一次远程请求就声称对方已锁库存、扣费或完成出库。技术行为无法可靠映射为用户可感知的规则时，不强行写进业务知识。

## 自然段与整句切分

一个段落围绕一个业务问题展开，通常先说明场景和对象，再说明处理过程、结果及限制。规则的条件和例外尽量同段保留；用明确业务名词替代“它”“上述状态”，但不机械地在每一句重复完整系统名称。适合分句的关键规则句要包含对象、条件和结论，不以串联许多分号制造超长句。

不合格：“该服务先调用方法 A，再调用方法 B；依据某个源码位置。”

合格的虚构写法：“在演示订单系统中，审核中的销售订单暂不支持人工取消，用户需要先完成审核处理，才能按订单所处阶段判断后续操作。允许取消的订单在处理成功后显示为已取消，但取消完成不代表款项已经退回，退款结果需要单独确认。”

上例只演示自然语言和段落结构。用于实际系统时，每项条件及后续动作都必须先经取证；缺少“先完成审核”证据就不写这个建议。正文不能用“源码未见”“静态实现”“调用函数”等审计语言解释未知，应写“当前资料不能确认退款是否自动发起”等用户能理解的必要边界，详细原因记在 analysis/。

## 知识正文不得出现的材料

不放代码片段、代码围栏、反引号代码、源码路径和链接、类/方法名、接口 URL、SQL、表/字段名、原始枚举值、commit/哈希、行号、知识/证据/场景 ID 或每段审计括注，也不要隐藏在 HTML 注释里。状态必须解释成已核实的业务名称；无法核实名称和含义时留待确认，不能猜测翻译。

OMS、WMS、渠道名称、真实业务单号等本身属于业务概念，可以正常使用；禁止的是用程序符号替代业务解释。系统技术架构、部署方式和实现机制不混入业务规则，除非用户另行请求技术文档，且该类资料应另行交付。

产品假设和未验收计划默认留在 analysis/，不能作为现状问答答案。系统的产品背景缺乏资料时写清已知业务定位及范围，不编造市场背景或收益。必要的业务未知可在“适用边界”说明，不让每段都充斥调查免责声明。

## 图表

纯业务流程、状态和决策表可辅助理解，但正文必须有等价文字。图源留在 analysis/diagrams/，不要把 Mermaid 或其他图表源码导入知识库。宿主可渲染时可以在正文附渲染图片；不能渲染就使用文字步骤/表格，明确实际验证情况。图节点和连线也用业务名称，未经证实的环节不能画成完成路径。

## 私有证据映射与导出

文档的系统、模块、主题、别名、稳定 ID、来源快照只保存在 analysis.json 的 documents 映射与清单中，导入器不需要理解它们。文档映射示例：

```json
{
  "path": "knowledge/modules/orders/order-cancellation.md",
  "claim_ids": ["C-CANCEL"],
  "scenario_ids": ["S-CANCEL"],
  "knowledge": {
    "id": "KB-ORDER-CANCEL", "kind": "topic", "parent_id": "KB-ORDER-MODULE",
    "system": "订单系统", "module": "订单管理", "topic": "订单取消", "aliases": ["撤单"]
  }
}
```

元数据规则沿用证据契约：id 稳定且全包唯一；kind 为 system/module/topic/cross_system/glossary；一个 system 根的 parent_id=null，module/cross_system/glossary 归属 system，topic 归属 module；module/topic 需要 module 文本。引用的结论、反证和证据必须存在，正文不出现这些 ID。需要更细追溯时可在 analysis/ 记录标题到结论的关联，不能把编号塞回知识正文。

按 Skill 入口运行 validate_analysis.py，再运行 export_knowledge.py；成功 stdout 清单另存 analysis/knowledge-manifest.json，失败时不覆盖旧清单。导出器检查私有映射、路径、层次、哈希、基础二级小节/说明段落及明显代码/审计残留。它不是完整 Markdown 渲染器，也不能证明段落的内容深度、事实正确或检索命中。不能仅因为脚本通过就标成知识质量通过。

更新时按稳定 ID 与哈希确认替换、重命名及撤回范围，列出应撤回的旧知识 ID，避免新旧矛盾答案共存；不自动上传、删除或修改 PG。

## 读者验收

抽一篇系统总览、一篇模块说明、一篇复杂主题，回答：不懂编程的读者能否说清功能、角色、主要步骤、条件、异常及最终结果？去掉标题后抽查规则段落/句子，能否保留必要的业务上下文？核对每个已确认步骤的证据和边界，尤其拒绝从枚举或接口名补闭环。记录实际已检查范围及未解决问题。

如果产物仍是逐接口摘要、同一长句模板反复出现、只有一级标题、全表格或假设混入现状，即使私有清单齐全也需要返工。先修复归纳方法，再重写；不能只用正则删除源码后缀并声称内容已合格。模拟切分不是 PG 检索测试。
