# 多仓库交接与数据库取证

## 多仓库业务图

为仓库、部署单元和业务域分别建立索引。不同仓库的相同类名不等于同一业务对象；同一状态码也可能有不同语义。记录对象标识转换（如 id / code / external_no）、归属系统、事实来源和最终写入责任。

HTTP/RPC 按客户端调用、HTTP 方法与路径、服务配置、请求响应字段、业务错误和重试逻辑核对。事件按生产者、topic/routing key、类型/版本、消费者注册、payload 字段与关联键核对。配置常量只是线索，还需找到实际使用点。

交接边保留双方源码证据、同步/异步语义、触发条件与结果责任。一端缺失标 one_sided；版本、字段或状态含义不一致标 conflict。已知存在代理或适配层时追踪该层，不能为填闭环假设它存在。共享表不等于事务一致性，远程调用成功也不等于后续业务成功。

对异步过程检查发送与本地状态更新顺序、事务边界、outbox、幂等、超时、重试、补偿、死信和人工处理的实际证据。没有实现材料的环节转为问题，不写成通用架构建议冒充现状。

术语必须结合状态写入点和下游使用解释；例如看似“已送达”的标识可能仅代表仓库交接。只有当前范围确实支持其终态含义才结束业务链，否则明确本系统边界和外部后续未知。

## 数据库操作边界

使用宿主已配置、已授权的 dbhub 或等价连接。查询前确认数据源别名、环境、schema、租户及仓库对应关系；多个相似数据库无法确定时不猜测。只在已授权范围做元数据、只读聚合及必要的最小脱敏样本读取，不执行 DML/DDL、存储过程、业务函数、迁移或测试写入。

检查工具端只读限制和数据库账号权限；dbhub 的 readonly、max_rows 是工具级设置，不能用 Skill 的文字要求替代权限。不得自动更改连接配置。无连接、权限不足或查询失败时保留失败记录，继续静态分析。

先元数据再业务命题：

1. 查看表、字段、约束、索引、注释和代码映射，识别真实业务对象与关联方向。
2. 为具体问题设计查询，如某状态使用情况、关联缺口或时间先后；说明需要什么证据才能支持或反驳陈述。
3. 明确数据粒度、关联基数、时间范围、时区、租户、软删除和历史版本；先去重/分组，避免一对多 join 放大数量。
4. 遵守现有超时、扫描和返回量预算。优先小范围/聚合查询；LIMIT 限制返回不保证扫描成本。昂贵查询预算不明时不执行。
5. 记录 SQL 和结果口径。少量样本、零行、截断及测试数据均有局限；不能推出规则普遍成立或生产能力已启用。

保留 SQL、查询时间、环境、过滤和脱敏聚合结果，使读者能检查观察依据。失败查询不作为“没有数据”的证据。源码与数据不一致时考虑历史数据、环境配置和版本差异，先记录冲突再解释。

## 恢复与工具上下文

记录每次语义工具所指向的项目。Serena 需切换项目时按仓库顺序操作，切换后验证项目标识；跨仓库并行工作只在工具会话相互隔离时使用。不要求多 Agent。跨库没有可靠关联键时保留未匹配关系，不通过字符串近似强行合并。
