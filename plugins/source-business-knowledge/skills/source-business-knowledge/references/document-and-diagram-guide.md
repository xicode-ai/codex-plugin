# 业务文档与图表表达

知识文档布局、段落写法和导入边界以 [knowledge-document-guide.md](knowledge-document-guide.md) 为准。本文件补充表达方式；不再生成一套与 knowledge/ 重复的平铺 PRD 或源码审计文档。

## 系统、模块与主题

系统总览先讲服务对象、职责边界和主要业务能力，再解释模块间配合；背景和目标有依据才写。模块说明讲该业务环节的输入、能力和输出，不列控制器或数据表。主题文档用二级小节组织真实的场景、流程、规则、异常和结果，每个小节都有自然段解释。

知识层次是“由总到分”的阅读组织，不要求知识库自动理解父子关系。总览只概括能力与协作，细规则以主题为主要版本，避免相同规则在多页完整复制后逐渐产生冲突。相关文档可用普通 Markdown 链接串联，关键结论仍在本段说清。

## 表达方式选择

| 需要解释的问题 | 表达方式 |
| --- | --- |
| 谁负责什么、业务范围是什么 | 简明说明与职责表 |
| 业务怎样推进、失败后怎样处理 | 业务流程文字步骤，必要时附流程图 |
| 多系统如何交接、谁确认结果 | 协作步骤与职责表，必要时附时序图 |
| 单据处于什么阶段、何时允许操作 | 中文业务状态说明与条件表 |
| 多条件如何影响结果 | 决策表及关键规则的自然段说明 |
| 系统职责边界需要整体呈现 | 业务视角的 C4 Context/Container 图，细节放附属资料 |

图与表都是补充，不能替代所有段落。图中节点只用业务名称，不画类、方法、接口、数据库字段或技术调用链。未确认的交接标明边界，不能把“已发送申请”画成“业务已完成”。

## 图源、图片与证据

图源只保存在 analysis/diagrams/，知识正文不嵌入代码围栏或 Mermaid 源码。可用宿主渲染工具生成图片后按需附图，正文同时保留文字；无渲染器时用业务步骤和表格即可。图片、图源、正文之间的审计映射保存在 analysis/，不把证据编号或源码位置写在业务图例中。

交付前核对标题层次、段落、链接和图示；实际渲染过才报告图示视觉检查通过。结构校验、人工业务核对、知识库实际检索是不同验证，分别报告。
