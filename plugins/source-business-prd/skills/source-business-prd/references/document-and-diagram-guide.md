# 产品文档与图表

## 阅读路径与现状 PRD

首页先给“系统服务谁、关键能力、核心业务怎样结束、当前发现的断点”，然后链接证据与细节。首页注明分析范围、仓库快照、数据库环境、实际覆盖、限制及最后采集时间；不要让读者从技术目录自行拼业务。

小系统可合并为一份 Markdown；复杂系统按领域拆分，默认建议：

| 文件 | 内容 |
| --- | --- |
| README.md | 阅读导航、关键结论、范围、覆盖与验证 |
| system-overview.md | 角色、目标、系统边界、价值依据与假设 |
| capability-map.md | 按业务目标组织的能力树和术语表 |
| domains/*.md | 分业务域现状 PRD |
| business-lifecycle.md | 核心对象生命周期、场景及异常闭环 |
| integrations.md | 跨系统职责、交接标识、契约与缺口 |
| data-model.md | 业务实体关系、约束及可用数据观察 |
| questions-and-conflicts.md | 冲突、待确认项及独立的未来建议 |
| analysis/analysis.json | 结构化证据、陈述、场景、覆盖及继续执行状态 |

每个领域 PRD 描述目标用户、问题、范围、场景、输入输出、主流程、规则、状态、权限、异常及现状验收示例。商业目标与动机标注依据或假设；验收示例核对现有行为，不把新增的理想规则写成已实现要求。没有页面证据时只描述业务操作，不发明按钮、布局或用户文案。

每个关键陈述带类型及证据引用，用 `claim:C-001`、`scenario:S-CANCEL` 绑定检查点。为读者提供 ID 到 evidence 的索引及具体源码路径/符号/行号；本地源码链接按交付环境生成，不能伪造远程链接。绝对路径可能含个人信息，分享前适当脱敏或改用仓库 ID + 相对路径。

## 表达方式选择

| 解释目标 | 合适表达 |
| --- | --- |
| 系统与使用者/外部依赖 | C4 System Context |
| 应用、服务、存储和职责 | C4 Container；需要时再展开组件 |
| 角色之间的业务步骤 | 流程图/泳道图 |
| 一次场景的服务交接 | 时序图/C4 Dynamic |
| 对象状态和转换条件 | 状态图 |
| 数据采集、转换、使用与去向 | 数据流图 |
| 业务对象及关系基数 | ER 图 |
| 多条件决策 | 决策表 |

C4 不等于所有图表，不要求强行补齐四层。Mermaid 是默认可移植表达；C4 若渲染环境不支持可用明确标注层级的 flowchart 表达，说明采用了 C4 的边界和职责视角。用户要求 draw.io、SVG 或特定工具时使用宿主可用能力，核心交付仍保留可读说明。

每张图只讲一个边界或一个场景；节点、状态、事件和交接使用正文相同术语。图中步骤或紧邻证据表引用相同 claim/scenario ID。只有代码可见的条件、回调入口或孤立函数，不能被画成“调用方已经调用”“状态自然相继发生”。没有初始创建证据就不画已证实初态；未知边、计划功能、关闭开关及不匹配消息必须可识别。

图源放入 Markdown 围栏或 diagrams/*.mmd；必要时附可编辑/渲染文件。为图提供等价的步骤或关系表，使不支持 Mermaid 的阅读器仍能理解业务。若宿主有图表技能或渲染器，按实际图种使用并渲染检查；否则明确未渲染，不声称图表视觉验证通过。

## 交付审查

1. 检查点结构校验通过，源码哈希/行号和输出映射核对。
2. 逐条核对关键规则引用内容；图、表、正文状态含义一致。
3. 按入口/能力/场景/仓库说明已分析、受阻和排除范围，不能用字数证明完整性。
4. 检查本地与外部链接、锚点、表格及图表；脚本只覆盖基础链接和围栏，其他检查需实际执行或说明未执行。
5. 用产品读者视角复述一个正常场景、一个失败场景和一个跨系统交接，能找到依据与未解决点。

报告脚本检查、图表渲染、真实数据库查询和运行验证各自的实际状态，不将结构合法等同于业务正确。
