# 从实现到业务理解

## 盘点与场景发现

先识别仓库与部署单元，再识别业务域；不要假设三者一一对应。查看适用规则、依赖描述、路由/API、菜单与权限、前端页面、事件消费者、定时任务、批导入、数据库迁移及已有需求。按实际入口发现候选能力，明确排除的目录和原因。测试和注释可提供调查线索，断言的预期行为仍需与实现核对。

优先建立“角色—业务对象—目标—触发—结果”的能力地图，再沿高价值或高关联的场景深挖。不能只扫 Controller，也不能逐个类写摘要后声称完整理解业务。记录尚未遍历的仓库、入口类型及发现盲区；覆盖分母随发现更新。

## 场景调查卡

每个场景回答下列问题，未知项进入 question claim：

| 方面 | 调查内容 |
| --- | --- |
| 目标 | 谁发起，想完成什么，价值是已知意图还是假设？ |
| 触发与前置 | 页面/API/任务/事件入口是什么，身份和对象应满足什么条件？ |
| 主流程 | 输入如何校验，决策如何执行，输出和持久化如何发生？ |
| 业务规则 | 状态、数量、金额、日期、租户、权限、库存等有哪些条件和边界？ |
| 状态 | 哪个对象从什么状态到什么状态，触发条件及终态具体含义是什么？ |
| 交接 | 哪个系统负责下一步，传递什么标识，怎样确认结果？ |
| 异常 | 失败、拒绝、取消、超时、重试、补偿、重复与人工干预如何处理？ |
| 结束 | 本场景何时完成，整体业务是否还有后续，谁可看到结果？ |

不要求所有场景都有全部异常机制。未找到实现时写“在已分析范围未见证据”，附检索范围，不直接写“系统没有此能力”。状态方法没有校验前态时如实描述，不替产品补出合法状态机。

追踪动态派发实现、依赖注入、策略注册、配置开关、profile 和运行条件。分别标记代码存在、入口可达、配置可启用和运行时已观察；不能相互替代。旧实现、迁移入口和孤立工具函数单列，不能直接并入主流程。

## 可核对的来源

读取结果需绑定当前仓库 ID 和路径；符号及行号以当次实际文件为准。Serena 行号如为 0-based，转为契约中的 1-based。截断片段、工具空返回或读取失败都不代表文件为空。不能把相邻文件或一次批量结果中的函数记到错误文件。写事实陈述之前回看其绑定的片段，图表也使用这些引用。

每份源码证据的哈希覆盖完整文件字节，不能填所引用片段的哈希。取证过程中如文件变化，重新读取并更新证据或标记待复核。哈希/行范围校验只能检查快照定位，不能判断片段是否支持业务结论。

## 产品经理视角

按“角色—目标—障碍—系统动作—预期价值—依据”解释功能。商业动机、用户需求、效率收益及规划目标需要文档/访谈/数据的明确依据。

- 代码直接可见行为：implementation。
- 有范围与时间口径的查询结果：data_observation。
- 某版本文档描述的目标：documented_intent；未验收计划仍只是意图。
- 从实现推导的可能价值：product_hypothesis，写出 rationale 和待验证问题。
- 缺失信息或证据分歧：question；相关 claim 保存反证 ID。

“审核中不能取消”可由实现条件支持；“为避免审核和取消相互覆盖”若无需求依据，保留为假设。若数据表明某状态使用量低，不能仅凭该观察建议下线功能。

## 长任务与复核

按场景完成一批后，先保存证据和陈述，再保存正文、图表和覆盖状态；文件写入成功前不标记本批完成。保留同一逻辑对象的稳定 ID，不因重排文档重新编号。修改已有分析前核对文件，合并用户修改，不覆盖并发编辑。

恢复时读取 run、仓库快照、coverage、limitations 与 next_actions，核对新 commit、工作区差异和来源哈希；根据引用关系复核受影响陈述、场景和文档。静态引用不能保证穷尽间接依赖，变更边界不清楚时扩大复核范围。数据库证据有独立时间点，需要重新验证时再查询，不以源码未变宣称数据仍然新鲜。
