# 全场景测试设计规则

## 需求追踪

从 PRD 提取稳定的需求编号、业务目标、角色、前置条件、主流程、分支、状态变化和验收条件。每个需求至少映射到一个用例；无法映射时记录覆盖缺口。

## 场景分类

每个业务流程至少评估：

| 分类 | 最小覆盖内容 |
| --- | --- |
| normal | 主流程、主要分支、成功响应和 DB 状态 |
| boundary | 最小/最大长度、数值边界、空集合、分页边界 |
| invalid | 缺失、类型错误、格式错误、非法枚举、无效关联 |
| permission | 角色、租户、资源、越权和认证失败 |
| idempotency | 重复请求、重复事件、同一业务键和并发重放 |
| state | 正向、逆向、乱序、重复和终态操作 |
| pagination | page/size、排序、过滤、空页、大结果集 |
| exception | 依赖失败、超时、冲突、事务回滚和错误映射 |

## API 与数据库断言

每个适用用例同时设计：

- API：HTTP 状态码、业务码、字段、数组数量、错误结构和响应状态。
- DB：记录存在性、状态、唯一性、关联关系、计数、时间和事务结果。

不能用 API 返回成功替代数据库一致性证据。只读查询用例如果没有业务持久化，可明确标记 DB 断言为不适用并说明原因。

## 状态和幂等

先从 PRD、接口契约和数据库字段建立允许状态转移表。对未确认的状态转移不发起写操作；对重复/乱序事件使用独立用例，验证第二次调用是否幂等或明确拒绝。

## 数据和环境

测试数据必须有前置查询、唯一标识、预期影响范围和清理方案。不要在不确定环境中复用看似相同的数据，也不要把生产数据作为测试夹具。
