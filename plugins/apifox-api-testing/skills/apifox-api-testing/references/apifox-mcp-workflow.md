# Apifox MCP 工作流

## 能力发现

先读取当前 Codex 会话提供的 MCP 工具名、描述和参数 schema，按能力匹配接口列表、接口详情和接口执行工具。优先识别以下历史上常见的别名：

- `listOpenApiEndpoints`
- `getOpenApiDetails`
- `executeOpenApi`

别名只用于匹配，实际调用必须使用当前暴露的工具和参数名。如果列表、详情或执行能力缺失，相关用例为 `BLOCKED`。

## 接口发现

1. 使用用户提供的环境标识和可用的项目/模块过滤条件。
2. 分页读取接口列表，直到工具返回完成标记或没有下一页。
3. 每页只保留接口 ID、method、path、标题、标签等索引字段。
4. 使用 PRD 业务词、模块、路径、HTTP method 和标签筛选候选接口。
5. 当候选过多时分批处理，不把完整接口目录复制到报告。

## 契约读取

对每个候选接口读取：

- path 参数、query 参数、header、body schema 和必填规则；
- 认证方式和环境依赖；
- 成功/失败响应结构、业务码和状态转换；
- 示例值、枚举、分页和幂等字段。

如果详情和 PRD 的业务语义冲突，先记录冲突并阻塞依赖该语义的用例，不自行修改接口契约。

## 请求和执行

执行前生成脱敏请求摘要。请求构造必须：

- 从契约填充 path/query/header/body；
- 从测试计划和 dbhub 数据计划获取业务数据；
- 不在日志或报告中输出认证值、Cookie、密码或完整请求体；
- 使用已解析的目标环境，不切换到相近名称的环境。

依据契约和业务语义分类副作用：

- 明确的 GET 查询或健康检查通常为只读；
- POST、PUT、PATCH、DELETE、取消、审批、提交等默认需要确认；
- 任何不确定的接口都需要确认；
- 即使 HTTP method 是 GET，只要会触发导出、刷新、生成或其他状态变化，也需要确认。

只读网络失败最多重试一次，且必须标记为 retry。写入、删除和状态变更不得自动重试，防止重复副作用。

## 结果证据

每次执行只记录：

- case ID、method、path、执行状态；
- HTTP 状态码和业务码；
- 必要响应字段是否存在、数量和状态摘要；
- 脱敏后的短错误摘要；
- 对应 dbhub 校验结果。

不要记录完整响应体、认证头、Cookie、密码、预约码、原始 SQL 参数或未经脱敏的错误堆栈。
